## 1. QUE ES KUKIA

Red descentralizada de computo GPU (estilo DePIN). Los nodos ejecutan tareas
reales de IA en sus GPUs y cobran en KIA. Fase: prototipo funcional en pruebas.
Sin precio, sin venta, sin promesas de rentabilidad.

## 3. CALENDARIO DE EMISION (garantia matematica, no estimacion)

El protocolo combina 3 mecanismos:

1. **Halvings por era** (predecible): la recompensa base se parte por la mitad
   cada ~20,71 anos. Era 0 = x1.0 (10 KIA base), era 5 = x0.03125.
2. **Recompensa dinamica** (persigue la fecha): cada pago se calcula como
   `restante / tareas_restantes_estimadas`, donde las tareas restantes se
   estiman con la tasa real de la red x segundos hasta el 13-04-2150.
   Limitada a bandas [0.1x, 10x] del halving para evitar spikes.
3. **Tope duro en el pago** (garantia absoluta): `pago = min(base x tier, restante)`.
   El ledger JAMAS supera 100.000.000. Verificado en codigo.

Efecto: si la red va lenta, el protocolo paga mas por tarea (para no quedarse
corto); si va rapida, paga menos (para no agotar antes). La fecha se persigue
activamente y el tope es matematico.

Estado actual (API real): `recompensa_base_actual = 100.0` porque la red de
pruebas hace ~7 tareas/dia (tasa baja -> objetivo alto, limitado a 10x).
Con mas actividad, baja solo. Comportamiento correcto y auditable.

## 4. DIFICULTAD ADAPTATIVA (potencia de LA RED, no mundial)

- `tops_red` = suma de TOPS declarados por los nodos conectados.
- Factor = sqrt(tops_red / 1747) limitado a [0.5, 4.0].
- Tamano de tarea (matriz n, inferencia n) escala con el factor.
- Si entran nodos -> tareas mas grandes (mantiene tiempo/tarea).
- Si se van -> tareas mas pequenas.
- Endpoint admin `/tareas/crear_auto` genera tareas con la dificultad actual.
- Visible en `/stats` -> `dificultad` (tops, factor, tamanos).

Red actual: 3.164 TOPS (factor 1.346, matriz n=344).

## 5. VERIFICACION (trustless, probada)

- El Core NO confia en el hash del minero.
- Recalcula la tarea el mismo (numpy CPU) y compara el RESULTADO EXACTO.
- Tareas deterministas con seed (checksums SHA256, matrices enteras acotadas).
- Correcto -> paga. Incorrecto -> 0 KIA + registro de rechazo.
- PROBADO: resultado correcto pagado (+10 KIA), resultado falso rechazado
  (el Core esperaba 3990, enviaron 999999999 -> 0 KIA).

## 6. BILLETERA (criptografia real)

- Claves Ed25519 reales (libreria `cryptography`, CSPRNG del sistema).
- Direccion = KUK + SHA256(clave publica) [estandar].
- Firma digital verificable (probada: firmar + verificar = True).
- **Recuperacion:** contrasena + 20 palabras unicas (lista BIP39 espanol,
  PBKDF2 200.000 iteraciones). Con ambas se recupera la MISMA billetera
  en cualquier equipo (probado: direccion recuperada identica).
- Clave privada nunca sale del equipo.

## 7. WORKER MULTI-GPU

- Detecta todas las GPUs CUDA, un hilo minero por GPU.
- Cada GPU se registra como nodo propio y mina en paralelo.
- Las 2 GPUs (5070 + 5060 Ti) trabajan simultaneamente.

4. "Doble pago posible" -> CORREGIDO: la tarea solo se cobra UNA vez. Segundo

## 13. FIXES DE CONCURRENCIA (revision 2, probados con hilos reales)

El revisor encontro 4 problemas mas profundos. TODOS corregidos y probados:

1. "Doble pago simultaneo" -> CORREGIDO: lock global de hilos (_pago_lock) +
   BEGIN IMMEDIATE (lock a nivel de fichero BD) + relectura del estado DENTRO
   del lock. PROBADO con 2 hilos simultaneos: solo 1 cobra (200+100), el otro 409.

2. "Tope 100M sin atomicidad" -> CORREGIDO: el calculo de restante + el pago
   ocurren DENTRO de la misma transaccion. Dos pagos simultaneos no pueden
   sumar mas del restante. Verificado en codigo (recompensa_pago dentro del lock).

3. "Fecha no garantiza reparto total" -> DOCUMENTADO honestamente: la fecha es
   objetivo que el protocolo persigue activamente (recompensa dinamica), el tope
   de 100M es garantia matematica dura. Si hay poca actividad quedan monedas sin
   emitir (no se inventan pagos). Asi esta escrito en el whitepaper.

4. "Tarea fallida reintentable" -> CORREGIDO: solo estado 'ejecutando' es pagable.
   'ok' -> 409, 'fallo' -> 409. PROBADO: reintento tras fallo = 409 bloqueado.

Evidencia concurrente (reproducible):
- 2 hilos pagan la misma tarea a la vez -> 1x200+100.0, 1x409. PAGOS_EXITOSOS=1.
- Todo en GitHub (commit ed9abb8, verificado en raw: _pago_lock, BEGIN IMMEDIATE).

## 15. AUTENTICACION DE NODOS POR FIRMA (revision 3, probado)

El revisor pidio verificar que un nodo no pueda suplantar a otro. IMPLEMENTADO:

- Registro con clave publica: POST /nodos/registrar acepta clave_publica (Ed25519 hex).
  Responde autenticado:true/false segun la traiga.
- Firma obligatoria: POST /tareas/resultado exige firma Ed25519 de "tid:metrica"
  cuando el nodo tiene clave registrada. Sin firma -> 401. Firma de otro -> 401.
- Worker firma cada envio con su billetera (WALLET.firmar).
- Nodos viejos sin clave siguen funcionando (compatibilidad), nodos nuevos van firmados.

PROBADO:
- Envio firmado correcto -> 200 ok:true + pago.
- Suplantacion (firma de otro) -> 401 'firma invalida (suplantacion bloqueada)'.
- Sin firma en nodo autenticado -> 401 'falta firma del nodo'.
- Todo en GitHub (commit 48ad054, verificado en raw: firma invalida, clave_publica,
  RateLimitMiddleware, _pago_lock, BEGIN IMMEDIATE, recompensa_pago, 2150-04-13).
